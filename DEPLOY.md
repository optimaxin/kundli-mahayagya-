# Deployment: backend on Render, frontend on Cloudflare Pages

```
Browser ──> Cloudflare Pages (static React site, https://<project>.pages.dev)
   │
   └──> Render web service (FastAPI, Docker, https://<service>.onrender.com/api/v1)
            └──> Supabase PostgreSQL via the IPv4 transaction pooler (port 6543)
```

The database is already migrated (0001-0003) and seeded in Supabase. Do the steps in this order:
the frontend needs the backend URL, and the backend needs the frontend URL for CORS.

## 1. Backend on Render

1. Render dashboard → **New → Blueprint** → connect GitHub → select this repository.
   Render reads [`render.yaml`](render.yaml) and proposes the service `mahayagya-api`
   (Docker, root `backend/`, region Singapore, health check `/api/v1/health`).
2. Render asks for the three secret values (`sync: false`). Enter them; the values to paste are in
   your local, git-ignored file `backend/.env.render`:

   | Key | Value |
   |---|---|
   | `DATABASE_URL` | The Supabase **transaction pooler** URL: `postgresql://postgres.<project-ref>:<db-password>@aws-0-ap-south-1.pooler.supabase.com:6543/postgres?sslmode=require`. Do **not** use the direct `db.<ref>.supabase.co` host: it is IPv6-only and Render has no IPv6. |
   | `DATA_ENCRYPTION_KEY` | A Fernet key: `python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"` |
   | `CORS_ALLOWED_ORIGINS` | The Cloudflare Pages URL, e.g. `https://kundli-mahayagya.pages.dev` (no trailing slash; comma-separate several, e.g. a custom domain too). |

   `JWT_SECRET_KEY` is generated by Render automatically. The rest is preset in `render.yaml`.
3. **Apply**. The first build takes a few minutes. Check `https://<service>.onrender.com/api/v1/health/ready`.
   It should return `"status": "ready"` and `"migration": "0003"`.
4. **Plan:** `render.yaml` uses the `free` plan, which sleeps after 15 minutes without traffic, so the next
   request waits about a minute. Switch to **Starter** or higher before registration opens.

The app refuses to start in production with a missing or weak `JWT_SECRET_KEY` or
`DATA_ENCRYPTION_KEY`, or with `CORS_ALLOWED_ORIGINS=*`. Check the Render logs if a deploy fails.

## 2. Frontend on Cloudflare Pages

1. Cloudflare dashboard → **Workers & Pages → Create → Pages → Connect to Git** → select this repository.
2. Build settings:

   | Setting | Value |
   |---|---|
   | Project name | `kundli-mahayagya` (gives `https://kundli-mahayagya.pages.dev`; it must match the CORS value) |
   | Production branch | `main` |
   | Framework preset | Vite (or None) |
   | Build command | `npm run build` |
   | Build output directory | `dist` |
   | Root directory | *(leave empty: repository root)* |
   | Environment variable | `VITE_API_BASE_URL` = `https://<service>.onrender.com/api/v1` |

   Node 22 is selected through [`.node-version`](.node-version). `VITE_API_BASE_URL` is baked in at build
   time, so after changing it, **retry the deployment**.
3. **Save and Deploy**. Security and caching headers come from [`public/_headers`](public/_headers). The app
   uses hash routes (`/#/register`), so no SPA redirect rules are needed.

### Hosting the frontend on Vercel instead

Import the repository in Vercel (framework: Vite, build `npm run build`, output `dist`). No environment
variable is needed: [`.env.production`](.env.production) already points the build at
`https://kundli-mahayagya.onrender.com/api/v1`. A `VITE_API_BASE_URL` set in the Vercel or Cloudflare
dashboard overrides it.

**Whichever host you use, its exact domain must be in Render's `CORS_ALLOWED_ORIGINS`.** Otherwise the
browser blocks every API call, and the session picker stays on "Loading…" (now "Unavailable" with an error
message). Example: `https://kundli-mahayagya.vercel.app,https://kundli-mahayagya.pages.dev`.

## 3. After both are up

1. If the Pages URL differs from what you entered for `CORS_ALLOWED_ORIGINS`, update it in Render
   (Environment) and let Render redeploy.
2. Create the first organiser account. Run it once, locally, against Supabase (it prompts for the password):

   ```bash
   cd backend
   .venv\Scripts\python -m scripts.create_admin --email <you@example.org> --name "Event Admin"
   ```

   Then add gate volunteers in `/#/admin` → Volunteers.
3. Smoke test: open `https://<project>.pages.dev/#/register` and check that seat counts load, log in at
   `/#/admin`, and check that the dashboard loads.
4. Pushes to `main` redeploy both automatically: Render through `autoDeploy`, Pages through its Git integration.

## Database changes later

New Alembic migrations are **not** run automatically on deploy. Run them from a machine that can reach
Supabase before deploying code that needs them:

```bash
cd backend
.venv\Scripts\alembic upgrade head          # uses DATABASE_URL / MIGRATIONS_DATABASE_URL from backend/.env
```

## Secrets checklist

- Secrets live only in Render's environment settings and in local, git-ignored `backend/.env` and
  `backend/.env.render`. Nothing secret is in this repository.
- The frontend gets only `VITE_API_BASE_URL`. Never give it Supabase keys: the browser talks only to the
  backend.
- The Supabase REST API is locked down (RLS on all tables and privileges revoked for `anon` and
  `authenticated`; see `backend/scripts/sql/supabase_hardening.sql`).
